# 从需求到测试用例

需求文档不是测试用例。中间必须经过一层**可判定的验收点（AC）**，否则用例只能靠临场发挥。

核心链路：

```
需求文档 → AC 编号 → TC 用例 → 执行结果 → 报告/Bug
```

每一层都必须能回链到上一层。

## 何时使用

适用：

- 拿到 PRD、原型、接口文档，要设计测试用例
- 要把一份需求拆成开发自测/QA 用例
- 要给已有功能补回归用例
- 要判断“需求、实现、数据”哪里不一致

不适用：

- 没有需求依据的纯探索测试
- 只需要执行已有用例、不需要设计
- 只改文案/样式且没有验收标准（先要 AC）

## 第一步：需求落盘

不要只把需求留在对话里。落成文件，至少记录：

```md
- 来源：文档 / 原型 / 链接
- 版本：v1
- 日期：
- 关联页面：
- 关联接口：
- 负责人：
```

同一功能后续更新时追加版本，不覆盖旧版本。

原则：**需求文件只写“要什么”，不写“怎么实现”。**

## 第二步：拆验收点（AC）

把需求正文拆成一条条可判定的 AC：

```md
| 编号 | 场景 | 前置条件 | 操作 | 预期 |
|---|---|---|---|---|
| AC-01 | 默认筛选 | 目标对象有归属分类 | 进入页面 | 选中对象所属分类 + 最新周期 |
```

每条 AC 必须满足：

- 有明确输入和可观察的预期
- 能用“是/否”判定
- 不依赖“体验流畅”“样式正常”这类主观描述
- 一条 AC 只表达一个行为

拆不出来时，标记为「待确认」，不要自己编一个预期。

### 常见 AC 类型

| 类型 | 示例 |
|---|---|
| 默认值 | 首次进入默认选中哪个 tab |
| 数据范围 | 返回全部还是前 N 条 |
| 格式 | 小数位、日期格式、单位 |
| 排序 | 升序/降序、同分如何处理 |
| 空态 | 无数据时显示什么、入口是否保留 |
| 错误态 | 失败提示、是否可重试 |
| 边界 | 0、null、空数组、越界、重复值 |
| 交互 | 切换、返回、滚动位置、并发竞态 |
| 权限 | 未登录/未购买/无权限 |

## 第三步：先做数据可用性审计

在写接口/界面用例前，先确认**需求依赖的数据是否真的存在**。

否则很容易把“后端没数据”写成“前端 bug”。

检查项：

- 接口是否有这个类型/字段
- 字段是否返回 `null` 或缺失
- 样本数据是否有非空值
- 空数组、全 0、字段缺失分别是什么表现
- 数据缺失是永久口径，还是当前样本/环境问题

输出一张表：

```md
| 指标 | 接口类型 | 返回行数 | 非空字段数 | 结论 |
|---|---|---:|---:|---|
| 金额 | amount | 20 | 0 | 有行无字段，数据缺口 |
| 数量 | count | 20 | 20 | 可用 |
```

**数据缺口不是前端缺陷。** 但要写进报告的「未闭合项」，并明确影响哪个 AC。

## 第四步：设计用例

按三层设计，不要只写 UI 点击步骤。

| 层级 | 适合验证 | 典型产物 |
|---|---|---|
| 逻辑层 | 计算、格式、排序、过滤、空值、状态映射 | 单元测试 / 表驱动测试 |
| 接口层 | 字段、结构、分页、权限、真实样本 | 只读接口探针 |
| 界面层 | 布局、多语言、tab、弹窗、滚动、返回 | 真机 checklist + 截图 |

### 用例表格式

```md
| 用例 ID | 对应 AC | 层级 | 场景 | 输入/数据 | 预期 | 优先级 | 状态 |
|---|---|---|---|---|---|---|---|
| TC-L-01 | AC-01 | 逻辑 | 默认排序 | 固定样本 | 降序 | P0 | 待执行 |
| TC-A-01 | AC-02 | 接口 | 字段存在 | 真实样本 | 有 statusCode | P0 | 待执行 |
| TC-U-01 | AC-03 | 界面 | 空态 | 空数据 | 显示“暂无数据” | P0 | 待执行 |
```

### 用例质量规则

- 一条用例只验证一个行为
- 写清输入/样本 ID，不写“随便找一场”
- 预期必须可判定
- 边界单独列，不混在正常用例里
- 同一条 AC 至少一条用例；P0 AC 至少一条可执行用例
- UI 用例写清入口、步骤、设备/语言

## 第五步：执行与报告

执行后更新用例状态：

```
待执行 → 通过 / 失败 / 阻塞
```

报告至少包含：

- 需求版本、用例版本、环境、设备
- 通过数 / 失败数
- 每个失败的复现步骤、期望、实际、责任方
- 未覆盖项及原因
- 数据缺口（如果有）

失败必须能对应到：

```
AC → TC → Bug ID / 外部问题
```

## 第六步：需求变更

不要重写全部用例，做 diff：

- 新增 AC → 新增 TC
- 修改 AC → 旧 TC 标「失效」，补新 TC
- 删除 AC → TC 标「废弃」，不直接删除
- 需求被确认作废 → 在需求文件和测试用例里都记录「已作废」，避免下次按旧需求回归

## 冲突分类

发现不一致时，先分类，再决定是否改代码：

| 类型 | 判定 | 处理 |
|---|---|---|
| 实现缺陷 | 需求明确、数据存在、代码行为不符 | 修代码 + 补回归用例 |
| 数据缺口 | 接口有行但字段为空 / 类型不存在 | 交数据/后端，不硬编码前端兜底 |
| 需求冲突 | 新原型与现有设计/实现口径不一致 | 先让产品确认版本，不直接改 |
| 环境问题 | 测试环境未部署/网络不通 | 列未闭合项，不算前端缺陷 |
| 用例错误 | 预期本身不可判定/写错 | 改用例，不改代码 |

⛔ 不要把“数据没有”当成“前端没做”
⛔ 不要把“原型这么画”直接当成“线上必须这样”，先确认版本
⛔ 不要把预期失败长期留在主测试套件里；要么单独成缺口报告，要么等确认后转成正常断言

## 输出

交付三份文件（或等价内容）：

1. **需求文档**：来源、版本、AC 表、数据依赖、待确认
2. **测试用例**：用例总览、分层用例、边界矩阵、未覆盖项
3. **测试报告**：结果、失败、数据缺口、结论

结论必须回答：

- 哪些 AC 已验证？
- 哪些失败是前端缺陷？
- 哪些是数据/环境等外部问题？
- 哪些还没覆盖？

## 约束

- 不编造接口路径、字段名或业务规则
- 不把没有数据的需求写成可执行断言后宣称“测试通过”
- 不用真实用户隐私数据做样本
- 不在 skill/文档里写密钥、token、内部地址或客户信息
- 需求变更必须留版本记录，不能静默替换
- 只读审计接口/数据，不做任何写操作
